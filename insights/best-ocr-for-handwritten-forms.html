Reading handwriting and extracting a handwritten form are different problems. A model can transcribe a cursive sentence at 99% character accuracy and still put the value in the wrong field, miss a ticked checkbox, or return a signature as the word "signature." A field test on 225 real handwritten form pages posted to r/computervision put field-level accuracy for the major cloud OCR APIs at roughly 65%, and the AIMultiple cursive benchmark (100 samples, 14 models, updated August 2026) shows the same engines well behind frontier vision-language models on raw transcription. If you are building intake, claims, or application processing, the number that matters is fields extracted correctly per form, not characters.

This guide compares five ways to get structured data out of handwritten forms: LlamaParse, Amazon Textract, Azure AI Document Intelligence, Google Document AI, and olmOCR for self-hosting. For general handwriting transcription across any document type, see our companion guide to the best AI for handwriting recognition. This page is about forms.

How we ranked these tools

We started from the tools developers name when they ask this question on r/computervision and Stack Overflow, and kept the ones that met four criteria:

  • A documented way to get structured output from a form: key-value pairs, checkbox state, signature detection, or schema-based extraction. Transcription-only tools were excluded (Transkribus, Pen to Print, HandwritingOCR.com).
  • A public API or a self-hostable model. No desktop-only software.
  • A distinct approach, so the list covers managed form APIs and an open-source model rather than five versions of one.
  • Published pricing.

This is a desk comparison. Facts come from each vendor's documentation, pricing pages, and release notes, dated where we could date them. Where we quote accuracy we say whose benchmark it is. LlamaParse is a LlamaIndex product, and the forms numbers we cite for it come from ExtractBench, LlamaIndex's own public benchmark (370 enterprise documents, 169 of them regulatory and tax forms). Treat it the way you would treat any vendor benchmark, then run your own 50 pages.

1. LlamaParse

LlamaParse is LlamaIndex's agentic document parser. It still does OCR, but it does not stop there: a layout model segments the page, an orchestrator routes each region to the right OCR model, LLM, or VLM, and validation loops check the result before it is stitched back into Markdown or JSON with bounding boxes. For a handwritten form, that means a scribbled value stays attached to its printed label and a ticked box comes back as a ticked box, not as stray pixels. Extraction is the second half of LlamaParse: you give it a schema (claim number, date of loss, checkbox for "vehicle driveable") and it returns typed fields with per-field confidence and a citation back to the page region.

That split is why it leads this list. Field-level extraction is what forms work actually needs, and on ExtractBench, which includes 169 regulatory and tax forms with hand-placed bounding boxes, LlamaParse Agentic Plus scored 95.6% value F1 at 8.1 cents a page, Agentic 89.5% at 3.1 cents, and Cost Effective 86.8% at 1 cent. The next-best system, an agentic loop on GPT-5.5, reached 93.6% at 27.8 cents a page and returned no grounding at all. LlamaParse Agentic also leads ParseBench (84.9%, April 2026), LlamaIndex's parsing benchmark on about 2,000 enterprise pages.

Core features

  • Layout-aware parsing that maps handwritten values to their labels, table cells, and sections instead of emitting flat text.
  • Schema-based extraction with field-level confidence scores and page-region citations for human review.
  • Four parsing tiers (Fast, Cost Effective, Agentic, Agentic Plus) and a Cost Optimizer that routes only hard pages to the expensive tier.
  • Natural-language parsing instructions, so you can say "treat the initials box as a signature" without writing regex.

Primary use cases

  • Handwritten intake and claims packets in insurance: incident descriptions, checkboxes, and signatures across variable layouts.
  • Patient intake forms and clinical notes where a wrong field is a safety problem, not a formatting problem.
  • Tax and lending forms where handwritten numbers and nested tables feed financial automation.

Recent updates

  • ExtractBench (August 2026): public extraction benchmark; LlamaParse Agentic Plus scored 95.6% F1.
  • Extract v2.5 (2026): document extraction agents with a Turbo tier (35 credits a page, no separate parse step).
  • ParseBench (April 2026): public parsing benchmark; LlamaParse Agentic scored 84.9% overall.

Watch out for

  • It is a hosted API. Standard plans process documents in LlamaIndex's cloud; data-residency teams need the Enterprise plan's private VPC deployment.
  • Agentic Plus costs 45 credits a page for parsing alone. Use the Cost Optimizer or route clean pages to Cost Effective, or the bill climbs fast.
  • The benchmark is LlamaIndex's own. It is public and the documents are available, but test your forms before you trust the number.

Integration and cost

  • Output: Markdown, plain text, or JSON with bounding boxes from parsing; typed JSON matching your schema, with confidence and citations, from extraction.
  • Integration: hosted REST API with Python and TypeScript SDKs. No infrastructure to run.
  • Cost at scale: 1,000 credits cost $1.25. Parsing runs 1 to 45 credits a page by tier; extraction runs 8 (Cost Effective), 25 (Agentic), or 60 (Agentic Plus) credits a page including the parse. The free plan includes 10,000 credits a month. Details on the pricing page.

2. Azure AI Document Intelligence

Azure AI Document Intelligence (the service formerly called Form Recognizer) covers the forms problem with three models. Read is OCR with a per-line isHandwritten flag. Layout adds tables, selection marks, and, with the keyValuePairs feature, label-value extraction without training. Custom extraction models, trained on as few as five labeled examples, add typed fields and signature detection.

What it does not do is reason about a messy page. If a handwritten value overlaps two labels or a checkbox is half-ticked, Layout returns its best geometric guess with a confidence number, and the normalization logic is yours to write. Teams on the Microsoft stack get a lot of that glue for free in Power Automate and Logic Apps; everyone else is writing it by hand.

Core features

  • Layout model with keyValuePairs, selection marks, tables, and Markdown or JSON output.
  • Custom neural models with labeled training and signature detection (v4.0, GA November 2024).
  • Container deployment for on-premises or disconnected processing.

Primary use cases

  • Claims and medical forms with mixed printed labels and handwritten entries.
  • Standardized intake forms where a custom model can be trained once and reused.
  • Microsoft-centric automation tied to SharePoint, Power Automate, and Azure storage.

Recent updates

  • March 2026: prebuilt US tax form models updated for 2025 forms, with multi-copy extraction (several W-2s in one document).
  • November 2024: v4.0 API GA, adding signature detection for custom neural models and Markdown output.

Watch out for

  • The pricing page does not render prices for every region; confirm the per-1,000-page rate in the Azure Pricing Calculator for yours.
  • The free tier (500 pages a month) excludes premium features, so you cannot evaluate custom models on it.
  • Custom models need labeled training data per form layout; a new form version means a new training run.

Integration and cost

  • Output: JSON with bounding polygons and confidence; Markdown from Layout in v4.0.
  • Integration: REST API or Python, .NET, Java, and JavaScript SDKs; Docker container for self-hosting.
  • Cost at scale: Read about $1.50 per 1,000 pages, Layout and prebuilt models about $10 per 1,000 pages, custom extraction about $50 per 1,000 pages (list prices, October 2026; confirm in your region). 500 pages a month free.

3. Google Document AI

Google Document AI splits the job into processors. Enterprise Document OCR reads the text and can flag handwritten words with a font-style add-on. Form Parser extracts key-value pairs, checkboxes (with filled or unfilled state), and simple tables, pre-trained, across 200+ languages. Custom Extractor is where it gets interesting: since January 2026 it runs on Gemini 3 and, in preview, Gemini 3.5 Flash, and June 2026 added validation and correction rules written in CEL. It is the big-three API that has moved furthest toward the agentic approach.

Form Parser is also the most expensive per page of the three for its baseline job, and it has real gaps: no radio buttons, no signature detection, no cells that span rows, and it cannot be up-trained on your documents. For a handwritten form that matches its assumptions it works; for anything irregular you are either writing CEL rules in Custom Extractor or calling Gemini directly.

Core features

  • Form Parser: key-value pairs, checkbox state, simple tables, 11 generic entity types.
  • Custom Extractor on Gemini with document-level prompting and CEL validation rules.
  • Layout Parser with image and table annotations (GA May 2026).

Primary use cases

  • Multilingual handwritten forms, where 200-language coverage matters more than cursive precision.
  • Custom extraction for a defined document type with fine-tuning on your own labeled set.
  • GCP pipelines feeding BigQuery or Vertex AI.

Recent updates

  • September 2026: Custom Extractor v3.1 Lite on Gemini 3.1 Flash Lite (preview) with fine-tuning and US/EU serving.
  • July 2026: Custom Extractor v3.5 on Gemini 3.5 Flash (preview).
  • June 2026: validation and correction rules in CEL for Custom Extractor (preview).
  • January 2026: Gemini 3 Pro and Gemini 3 Flash versions of Custom Extractor and Layout Parser (preview)

Watch out for

  • No signature detection in Form Parser; checkboxes may come back without a matching key.
  • Several of the newest Gemini-based processors are preview and some are flagged as not meeting data-residency standards.
  • Legacy processors were discontinued on June 30, 2026; check that your processor version is current.

Integration and cost

  • Output: JSON Document object with entities, bounding boxes, and confidence; Layout Parser returns chunked blocks.
  • Integration: REST or client libraries; processors are created per project and region.
  • Cost at scale: Form Parser $30 per 1,000 pages for the first million a month ($20 after), Custom Extractor $30 per 1,000, Enterprise Document OCR $1.50 per 1,000, Layout Parser $10 per 1,000 (list prices, October 2026).

4. Amazon Textract

Amazon Textract is the most form-literal API on this list. AnalyzeDocument takes a FeatureTypes list, and FORMS returns key-value pairs, selection elements (checkboxes and radio buttons) as key-value pairs, and SIGNATURES returns a bounding box and confidence for every signature it finds. QUERIES lets you ask "What is the policy number?" in plain English and get the answer in a separate block. That is a lot of the forms problem handled server-side, and if your pipeline already lives in S3 and Lambda it is the path of least resistance.

The ceiling is handwriting itself. Textract recognizes handwritten characters in English only, and both the r/computervision field tests and the AIMultiple benchmark put it mid-pack on cursive. It does well when handwriting sits inside a printed box next to a printed label. It does badly on narrative sections, overwritten corrections, and values that drift between fields.

Core features

  • FORMS, TABLES, QUERIES, LAYOUT, and SIGNATURES feature types, mixable in one call.
  • Selection elements returned with SELECTED or NOT_SELECTED status.
  • Block-level confidence on every word, line, key, and value.

Primary use cases

  • Loan applications, tax forms, and intake packets with stable layouts and boxed fields.
  • Signature presence checks on contracts and consent forms.
  • AWS-native pipelines with S3 triggers and asynchronous batch jobs.

Recent updates

  • Layout feature type (2023) returns reading-order blocks for paragraphs, headers, and lists; Custom Queries adapters let you fine-tune query answers on your own documents.

Watch out for

  • Handwriting recognition is English only. Non-English handwritten forms are out.
  • Synchronous calls accept one PDF page; multi-page forms need the asynchronous API and a job-polling loop.
  • Forms pricing is per feature, so FORMS plus SIGNATURES plus QUERIES on the same page is three charges.

Integration and cost

  • Output: JSON Block objects with geometry, relationships, and confidence; no Markdown.
  • Integration: boto3 or any AWS SDK; async jobs via StartDocumentAnalysis and SNS.
  • Cost at scale: Forms $0.05 a page for the first million pages a month ($0.04 after), Queries $0.015, Signatures $0.0035, Tables $0.015, text-only $0.0015 (US West list prices, October 2026). Free tier: 100 Forms pages a month for three months.

5. olmOCR

olmOCR is the open-source option that belongs on a handwriting list. It is a fine-tuned 7B vision-language model from the Allen Institute for AI, Apache 2.0, and it placed in the top three on the AIMultiple cursive benchmark alongside GPT-5 and Gemini 3 Pro. The model reads the whole page as an image and writes Markdown in reading order, with tables, equations, and handwriting handled in one pass. AI2 puts the cost at under $200 per million pages on your own GPUs. DeepSeek-OCR, the other open-source model that comes up, scored last on the same benchmark at 79%, so we would not start there for handwriting.

The catch for forms is that olmOCR outputs Markdown, not fields. A checkbox becomes a character or nothing; a signature becomes blank. To get structured data you add an LLM extraction step over the Markdown, which brings its own hallucination and confidence problems, or you treat olmOCR as the OCR layer under a tool that does extraction. It is the right choice when documents cannot leave your network and you have a GPU and an engineer to run it.

Core features

  • 7B vision-language model with handwriting, table, and equation support, Markdown output in reading order.
  • Batch pipeline for large back-file conversion, with vLLM serving.
  • olmOCR-Bench for evaluating output on your own documents.

Primary use cases

  • Privacy-bound handwritten records that cannot go to a cloud API.
  • High-volume, steady workloads where GPU time beats per-page fees.
  • The OCR layer in a self-built extraction pipeline.

Recent updates

  • October 2025: olmOCR-2-7B-1025 (v0.4.0) raised olmOCR-Bench to 82.4.
  • January to March 2026: v0.4.x releases added a PII tagging pipeline, parallel retries, and a more robust work queue.

Watch out for

  • No key-value, checkbox, or signature output. Structured extraction is a second step you build.
  • Needs a recent NVIDIA GPU with at least 12 GB of VRAM and 30 GB of disk; as a generative model it can drop or invent text.
  • You own serving, batching, retries, and upgrades.

Integration and cost

  • Output: Markdown (and Dolma format for dataset builds).
  • Integration: pip install olmocr with a local GPU, or point it at an external inference provider.
  • Cost at scale: free under Apache 2.0; under $200 per million pages in GPU time by AI2's estimate, plus the extraction step and operations.

Final thoughts

If you are choosing one tool for handwritten forms, start with LlamaParse. It is the only option here that reads messy handwriting at VLM quality and returns typed fields with confidence and citations, which is what makes a review queue work. On the forms-heavy ExtractBench set it leads at every price tier, and the free plan's 10,000 credits a month are enough to run your 50 hardest pages before you decide.

If your forms are fixed-layout and your stack is AWS, Textract's FORMS and SIGNATURES features will get you far. If you need handwriting in a dozen languages or on-prem containers, Azure Document Intelligence. If your forms are irregular and you want Gemini with validation rules, Google's Custom Extractor. If documents cannot leave your network and you have a GPU, olmOCR plus your own extraction step. And if you are tempted to just call Gemini: do it for the prototype, then come back to this list when the first hallucinated claim number reaches production.

Frequently asked questions

What does handwritten-form extraction cost at scale?

Per-page API fees are the small number. Human review is the big one. Here is a sample workload: 50,000 handwritten intake forms a month, two pages each, 100,000 pages, using October 2026 list prices.

Now the review column. Say each form has 20 fields, so a million fields a month. At 90% field-level straight-through processing, 100,000 fields go to a reviewer; at 95%, 50,000. At 10 seconds a field that is 280 versus 140 hours a month. The gap between a tool that extracts 87% of fields correctly and one that extracts 95% is about 220 review hours a month on this workload, which is more than the entire API bill for any option above. Tools that return per-field confidence let you route only uncertain fields; tools that return a flat JSON blob make you review everything or nothing.

Which tools detect checkboxes and signatures on handwritten forms?

Textract returns selection elements as SELECTED or NOT_SELECTED and signatures as bounding boxes with confidence. Azure Layout returns selection marks; signature detection requires a custom neural model. Google Form Parser returns checkbox state as a valueType but does not support radio buttons or signatures. LlamaParse returns both and lets you define a signature field in the schema so it comes back as a typed value with a citation. olmOCR can be prompted to describe them, but nothing guarantees the answer and there is no confidence attached.

How do I route low-confidence fields to human review?

Pick a tool that scores each field, not each page. Textract and Azure give block-level confidence on keys and values; Google gives entity confidence; LlamaParse gives per-field confidence with a citation to the page region. Set a threshold per field type, not globally: a date of birth needs a higher bar than a free-text comment. Then measure what fraction of fields fall below the threshold on 100 real forms, because that number, not the vendor's accuracy claim, is your review cost.

How do I benchmark handwritten-form OCR on my own forms?

Collect 50 to 100 real forms, weighted toward the worst handwriting and the most crowded layouts. Write down the correct value for every field you care about. Run each candidate and score at the field level: exact match for IDs and amounts, normalized match for dates and names, and state match for checkboxes. Track three numbers per tool: field accuracy, the share of fields below your review threshold, and cost per form including review time. Our document parser evaluation guide covers the mechanics, and ExtractBench is a useful public baseline because 169 of its 370 documents are forms.

What makes a handwritten form harder to parse than handwritten text?

Three things.

  • Values drift: a handwritten answer overlaps the next label or sits between two boxes, so the system has to decide which field it belongs to.
  • Modalities mix: checkboxes, signatures, initials, stamps, and corrections share the page with text and none of them is text recognition.
  • Layouts vary: the same form exists in several versions, so template matching breaks. Transcription accuracy is necessary and nowhere near sufficient; the question is whether each value lands in the right field.

What output format is best for handwritten forms in LLM and automation workflows?

Typed JSON that matches a schema, with a confidence score and a page citation per field. Markdown is the right output for retrieval and summarization over whole documents, but a form is a set of fields, and automation needs to validate and write those fields into a system. Bounding boxes or citations matter more here than anywhere else, because a reviewer correcting a handwritten value needs to see the handwriting.

Should I use a cloud API or self-host for handwritten forms?

Self-host when documents cannot leave your network, when volume is high and steady enough that GPU time beats per-page fees, and when you have an engineer to own serving and upgrades. Use a managed API when time to production matters more than control, when volume is spiky, or when your forms are hard enough that a wrong parse costs more downstream than the page fee. Many teams split it: a local model for clean, printed pages and a managed extraction API for the handwritten ones.
