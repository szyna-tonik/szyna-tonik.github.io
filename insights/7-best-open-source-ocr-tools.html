Open-source OCR has moved well beyond reading characters off a page. The newest tools reconstruct tables, reading order, and formulas, and several run a vision-language model end to end. That matters when the output feeds an LLM, where the hard part is preserving structure, not recognizing letters. The options now range from CPU-only engines you can install in a minute to GPU models that approach managed agentic document processing services.

In this guide, we compare seven open-source OCR tools you can run on your own infrastructure: LiteParse, Tesseract, PaddleOCR, DeepSeek-OCR, Docling, olmOCR, and EasyOCR. They range from classic CPU-only engines to newer vision-language models that need a GPU. We also cover where a managed service such as LlamaParse fits when open source isn't enough. By the end, you should have a practical sense of which platform best fits your stack, workload, and operational constraints.

Ranking Methodology

We started from widely used open-source OCR projects and kept the ones that met four criteria as of October 2026.

  • A recognized open-source license that permits commercial use (Apache 2.0 or MIT), checked against each project's repository.
  • A public release history and a maintained codebase. Where development has slowed, as with EasyOCR, the section says so.
  • A distinct approach, so the list spans classic engines, layout-aware toolkits, and vision-language models instead of seven variations on one.
  • Documented output formats and deployment options, so you can tell what you get back and where it runs.

This is a desk comparison. Details come from each project's repository, documentation, and release notes, and benchmark figures are quoted only where a project or a public benchmark reports them. LlamaParse sits outside the ranking because it is not open source. For independent numbers on parsing quality, see ParseBench, LlamaIndex's public benchmark of about 2,000 human-verified enterprise document pages.

1. LiteParse

LiteParse is LlamaIndex's open-source document parser, released under the Apache 2.0 license. It runs entirely on your own machine, with no cloud calls and no GPU, and turns PDFs, Office files, and images into layout-preserving text, Markdown, or JSON with bounding boxes. Rather than running a vision model over every page, it reads the text and layout signals already in the file and uses OCR for scanned pages and images.

That design makes it fast and cheap enough to sit inside an agent loop, a CLI script, or a browser tab. LiteParse ships as a CLI with Python, Node.js, Rust, and WebAssembly packages, and its OCR layer is pluggable: Tesseract is bundled by default, and you can point it at an EasyOCR or PaddleOCR server instead. It is a good starting point when your documents are mostly digital-born and parsing has to stay local.

Core features

  • Local, CPU-only parsing with no GPU, API key, or cloud dependency.
  • Markdown, layout-preserved text, and JSON output with bounding boxes.
  • Pluggable OCR: bundled Tesseract by default, or an external EasyOCR or PaddleOCR server.

Primary use cases

  • Fast local parsing of digital-born PDFs and Office documents for AI agents and LLM applications.
  • Privacy-sensitive workloads where documents cannot leave your infrastructure.
  • A first-pass parser that handles simple pages locally and flags complex ones for a heavier tool.

Recent updates

  • v2.1 (June 2026) added native Markdown output from a model-free, heuristic pipeline.
  • Later 2.x releases added complexity detection for routing documents before parsing and layout block classification with bounding boxes.

Watch out for

  • Accuracy drops on dense tables, multi-column layouts, charts, handwriting, and scanned PDFs; LlamaIndex's own documentation recommends LlamaParse for those.
  • Markdown output is heuristic, so it has an upper bound on accuracy compared with model-based parsers.
  • OCR quality on scans depends on the engine you plug in.

Integration and cost

  • Output: layout-preserved text by default, with Markdown or JSON with bounding boxes on request.
  • Integration: one install (pip install liteparse or npm i -g @llamaindex/liteparse) and one command, lit parse doc.pdf --format markdown.
  • Cost at scale: free under Apache 2.0. Model-free parsing runs at about 3 ms per page on CPU in LlamaIndex's own benchmarks.

2. Tesseract

Tesseract is the reference open-source OCR engine. Originally developed at HP and later sponsored by Google, it is now community-maintained under the Apache 2.0 license, and many other tools, including LiteParse, use it under the hood. Its LSTM-based recognizer supports more than 100 languages out of the box and runs comfortably on CPU.

Tesseract is strongest on clean, printed, single-column text: scanned letters, book pages, and simple forms. It returns plain text, hOCR, TSV, ALTO, PAGE XML, or searchable PDF. Its layout handling stops at page segmentation, so tables and multi-column reading order usually need extra work, and most production setups pair it with image preprocessing such as deskewing, binarization, and upscaling.

Core features

  • LSTM-based recognition engine with trained data for 100+ languages.
  • Output as plain text, hOCR, TSV, ALTO, PAGE XML, or searchable PDF.
  • Runs on CPU, with a mature ecosystem of wrappers such as pytesseract and Tesseract.js.

Primary Use Cases

  • Digitizing clean scanned documents and books into searchable text or PDFs.
  • Embedding lightweight OCR in desktop, server, or edge applications without a GPU.
  • Serving as the OCR backend inside larger parsing pipelines.

Recent Updates

  • The 5.x series is still actively maintained; the 5.5 releases focused on fixes to ALTO and PAGE XML output and memory-safety hardening.

Watch Out For

  • Accuracy falls sharply on low-resolution, skewed, or noisy scans without preprocessing.
  • No native table extraction, and complex layouts often come out in the wrong reading order.
  • Weak on handwriting.

Integration and Cost

  • Output: plain text by default, hOCR, TSV, or ALTO when you need word positions, and searchable PDF for archives.
  • Integration: install the tesseract binary plus a wrapper such as pytesseract, then add your own preprocessing and layout logic.
  • Cost at scale: free under Apache 2.0 and CPU-only, so the cost is server time and you scale by adding cores.

3. PaddleOCR

PaddleOCR is Baidu's open-source OCR toolkit, released under the Apache 2.0 license and one of the most-starred OCR projects on GitHub. It is less a single model than a family: the PP-OCR text detection and recognition models, PP-StructureV3 for layout and table parsing, and PaddleOCR-VL, a vision-language model for end-to-end document parsing.

That range is its main advantage. The lightweight PP-OCR models run on CPU and suit high-volume text recognition across 100+ languages, while PP-StructureV3 converts complex PDFs into Markdown or JSON with coordinates for tables and text blocks. Teams with a GPU can move up to PaddleOCR-VL for formulas, tables, and harder layouts. The trade-off is a larger framework to learn, and most pipelines run on PaddlePaddle rather than PyTorch by default.

Core Features

  • PP-OCR detection and recognition models in several sizes, from tiny CPU-friendly models to larger server models.
  • PP-StructureV3 layout, table, and formula parsing with Markdown and JSON output.
  • PaddleOCR-VL vision-language model for end-to-end document parsing.

Primary Use Cases

  • Multilingual OCR at scale, especially for Chinese, Japanese, and other non-Latin scripts.
  • Converting complex PDFs with tables and formulas into Markdown or JSON.
  • On-device or CPU-only OCR where model size and speed matter.

Recent Updates

  • v3.7.0 (June 2026) introduced PP-OCRv6, a unified model covering 50 languages with a reported 5.2x CPU speedup.
  • v3.6.0 (May 2026) shipped PaddleOCR-VL-1.6, which the project reports at 96.3% on OmniDocBench v1.6.

Watch Out For

  • Steeper learning curve: many models, pipelines, and configuration options to choose between.
  • Runs on the PaddlePaddle framework by default, which is less familiar to many teams than PyTorch.
  • The vision-language models need a GPU for practical throughput.

Integration and Cost

  • Output: text with bounding boxes from PP-OCR, and Markdown or JSON from PP-StructureV3 and PaddleOCR-VL.
  • Integration: pip install paddleocr, then pick a pipeline. Plan time for model selection and tuning.
  • Cost at scale: free under Apache 2.0. PP-OCR runs on CPU, while the vision-language models need GPU time.

4. DeepSeek-OCR

DeepSeek-OCR is one of the most compelling open-source options for teams that want local control and high-throughput OCR without recurring API charges. Rather than relying on a conventional detect-then-recognize stack, it uses a unified transformer approach that processes text, formulas, and charts together. That architecture makes it especially appealing for builders who want to modernize their document pipelines around multimodal models instead of legacy OCR components.

Its biggest differentiator is token compression. For teams running GPU inference at scale, that can translate into faster throughput and better memory efficiency, especially on dense, image-heavy documents. DeepSeek-OCR fits best in environments where engineering teams already have GPU infrastructure and want the flexibility to self-host, customize, and embed OCR directly into broader AI services.

Core Features

  • Token compression technology for faster and more memory-efficient GPU inference.
  • Unified transformer architecture for text, layout, charts, and formulas in one pass.
  • Compatibility with frameworks like vLLM and Hugging Face for flexible deployment.

Primary Use Cases

  • Large-scale GPU OCR for private or high-volume document workloads.
  • High-throughput OCR microservices that need rapid parallel processing.
  • Multimodal document extraction where text, formulas, and charts appear together.

Recent Updates

  • Released DeepSeek-OCR 2(January 2026) as the newest generation of its OCR stack.
  • Added upstream vLLM support (October 2025) for high-throughput serving.

Watch Out For

  • Requires GPU acceleration to be practical in production settings.
  • Can hallucinate details in dense or visually overlapping documents.
  • Demands more infrastructure work than managed cloud OCR services.

Integration and Cost

  • Output: Markdown, plus grounding boxes that tie text back to its position on the page.
  • Integration: run it through vLLM or Hugging Face Transformers on a CUDA GPU. You own model serving, batching, and retries.
  • Cost at scale: free under the MIT license. The repository reports about 2,500 tokens per second on a single A100 40 GB with vLLM, so budget for GPU hours instead of per-page fees.

5. Docling

Docling is a lightweight open-source choice aimed at teams dealing mostly with digital-born PDFs rather than poor-quality scans. Instead of treating every page as an image, it works well when a document already contains an accessible text layer. That makes it a practical fit for developers who want a fast, local path from enterprise PDFs to Markdown without introducing heavyweight multimodal inference.

For AI builders, Docling’s main appeal is simplicity. It can act as a clean ingestion layer for LLM applications where the source material is already relatively structured and machine-readable. It is not the best option for handwriting or degraded scans, but for digital documents, it offers an efficient and cost-effective workflow that is easy to operate on-premise.

Core Features

  • Markdown-first output optimized for LLM-friendly downstream use.
  • Digital document parsing that leverages native text layers for faster extraction.
  • Local deployment support for privacy-sensitive and on-prem workloads.

Primary Use Cases

  • Converting digital-born PDFs into structured Markdown.
  • Lightweight text extraction for standard business documents.
  • Feeding clean source content into LLM applications and search systems.

Recent Updates

  • Recent 2.x releases added the GraniteDocling vision-language model, chart understanding, and an MCP server.
  • Input support has expanded to email, EPUB, OpenDocument, audio, and video files.

Watch Out For

  • Struggles with scanned, low-resolution, or handwritten documents.
  • Can flatten complex layouts such as multi-column pages.
  • Depends on underlying OCR backends for non-digital text extraction.

Integration and Cost

  • Output: Markdown, HTML, DocTags, or lossless JSON.
  • Integration: pip install docling. It runs locally, including in air-gapped environments.
  • Cost at scale: free under the MIT license. It runs on CPU, with optional GPU acceleration for its layout and table models.

6. olmOCR

olmOCR is an open-source toolkit from the Allen Institute for AI (AI2) for converting PDFs and document images into clean, linearized text. It is built around a fine-tuned 7B vision-language model and released under the Apache 2.0 license. Where classic engines recognize characters line by line, olmOCR reads the whole page as an image and writes out Markdown in natural reading order.

That makes it a strong fit for the documents that trip up traditional OCR: scanned PDFs, multi-column papers, tables, equations, and handwriting. It is designed for batch conversion at scale, and AI2 puts the cost at under $200 per million pages on your own GPUs. The catch is hardware. You need a recent NVIDIA GPU with at least 12 GB of VRAM, and, like any generative model, it can occasionally produce text that is not on the page.

Core Features

  • Fine-tuned 7B vision-language model that outputs Markdown in natural reading order.
  • Handles tables, equations, handwriting, and multi-column layouts in a single pass.
  • Batch pipeline built for large-scale PDF conversion, plus the olmOCR-Bench benchmark for evaluating output.

Primary Use Cases

  • Converting scanned and image-only PDFs into clean Markdown for LLM applications.
  • Parsing academic papers and technical documents with equations and tables.
  • Large back-file conversion jobs on self-hosted GPUs.

Recent Updates

  • v0.4.0 (October 2025) shipped a new model that raised its olmOCR-Bench score by about four points, to 82.4.

Watch Out For

  • Requires a recent NVIDIA GPU with at least 12 GB of VRAM.
  • As a generative model it can hallucinate or drop text, so output needs validation for high-stakes data.
  • Slower per page than classic OCR engines, and more than you need for clean digital PDFs.

Integration and Cost

  • Output: Markdown in natural reading order, plus Dolma format for dataset builds.
  • Integration: pip install olmocr with a local NVIDIA GPU, or point it at an external inference provider.
  • Cost at scale: free under Apache 2.0. AI2 estimates under $200 per million pages on your own GPUs.

7. EasyOCR

EasyOCR is a PyTorch-based OCR library from Jaided AI, released under the Apache 2.0 license. Its appeal is in the name: a few lines of Python give you text detection and recognition in 80+ languages, with no separate engine to install or configure. Under the hood it pairs a CRAFT text detector with a CRNN recognizer.

EasyOCR returns each detected text region with its bounding box and a confidence score, which makes it handy for scene text, screenshots, receipts, and other images where you need to know where the text sits. It runs on CPU and is faster on a GPU. It does not understand document structure, though, so there is no table extraction, Markdown output, or reading-order reconstruction.

Core Features

  • Ready-to-use detection and recognition for 80+ languages across multiple scripts.
  • Returns bounding boxes, text, and confidence scores for each region.
  • Simple Python API with both CPU and GPU support.

Primary Use Cases

  • Quick prototypes and proofs of concept that need OCR in a few lines of code.
  • Text extraction from photos, screenshots, signs, and scanned images.
  • A multilingual OCR backend for other parsers, including LiteParse.

Recent Updates

  • Release cadence has slowed; the latest tagged release is 1.7.2 (September 2024).

Watch Out For

  • No layout analysis, table extraction, or structured output.
  • Handwriting is not supported yet; it remains on the project's roadmap.
  • Development is slower than on newer projects, so accuracy on complex documents trails vision-language models.

Integration and Cost

  • Output: a list of bounding boxes, text, and confidence scores, one entry per detected region.
  • Integration: pip install easyocr and three lines of Python.
  • Cost at scale: free under Apache 2.0. It runs on CPU and is faster with a GPU.

When open source isn't enough: LlamaParse

LlamaParse is not open source. It is LlamaIndex's managed document parsing service, which is why it sits outside the ranking above. It is here because it is the natural next step when your documents are too complex for the tools on this list, or when you would rather not run OCR infrastructure yourself.

If you are comparing other managed services, such as Amazon Textract, Google Cloud OCR, Azure OCR, or Abbyy, see our guides to the best OCR software and the best OCR APIs.

LlamaParse represents a meaningful shift away from traditional OCR pipelines that only extract raw text. Instead of flattening multi-column pages, nested tables, charts, and equations into noisy output, it reconstructs the semantic structure of a document so that the result is actually usable inside AI systems. For developers building production extraction workflows or agentic document systems, that difference matters. The output is not just readable text, but structured content that preserves context and layout.

LlamaParse is particularly strong for teams working with complex enterprise documents that routinely break conventional OCR. Financial reports, healthcare records, insurance packets, and scientific PDFs often contain the exact kinds of layout and multimodal complexity that legacy OCR mishandles.

By turning those inputs into clean Markdown and structure-aware outputs, LlamaParse helps technical teams reduce manual cleanup and improve downstream retrieval quality.

Final thoughts

If you are choosing one open-source OCR tool to start with, make it LiteParse. It installs with one command, runs on CPU with no GPU or API key, keeps documents on your own machine, and returns text, Markdown, or JSON fast enough to sit inside an agent loop. When your documents get harder than open source can handle, LlamaParse is the best option. It ranks first on ParseBench, LlamaIndex's public benchmark of about 2,000 enterprise document pages, and there is nothing to host. It is especially well suited for developers building intelligent retrieval systems, extraction pipelines, and agentic document workflows where layout fidelity matters as much as raw text accuracy.

For technical builders working with complex, unstructured documents, the real decision is no longer just “Which OCR engine reads text best?” It is “Which system gives my LLM stack the cleanest, most faithful representation of the document?”

Open source removes the per-page fee. You pay in compute and engineering time instead.

CPU tools are effectively free for clean digital documents at any volume. GPU models are the cheapest per page for scans and complex layouts once you already operate GPUs. A managed service costs more per page and wins when engineering time is the constraint or hard documents need to parse correctly the first time.

When does managed OCR become more cost-effective?

Managed OCR is cheaper when running your own pipeline costs more in engineering hours than the per-page fee.

LlamaParse basic parsing costs $1.25 per 1,000 pages. GPU time for a self-hosted model like olmOCR costs under $0.20 per 1,000 pages. What is the difference between open-source and commercial OCR?

Open-source OCR is software whose code, and for model-based tools the model weights, is published under a license such as Apache 2.0 or MIT. You can run it on your own infrastructure, inspect how it works, and modify it. Our glossary entry on open source OCR models covers the main engines in more detail.

Commercial OCR is delivered as a managed API or a licensed product. You pay per page or per seat, and the vendor runs and updates the models. Open source gives you control over data, cost, and customization, and in exchange you operate it yourself. Commercial services take the infrastructure off your hands and usually handle harder documents out of the box. On this page, LiteParse is LlamaIndex's open-source parser and LlamaParse is its commercial, managed service.

How do I choose the right open-source OCR tool?

  • Start with your documents, then your hardware.
  • Digital-born PDFs and Office files: LiteParse or Docling.
  • Clean scans of printed text: Tesseract.
  • Multilingual documents or complex layouts on CPU: PaddleOCR.
  • Scans with tables, formulas, or handwriting, and a GPU available: DeepSeek-OCR or olmOCR.
  • Text in photos, screenshots, and other images: EasyOCR.

Then run your shortlist on 20 to 50 of your own pages, including the worst ones, before you commit. Published accuracy numbers rarely predict how a tool behaves on your documents.

Do open-source OCR models require a GPU?

Not all of them. LiteParse, Tesseract, Docling, EasyOCR, and PaddleOCR's PP-OCR models run on CPU. DeepSeek-OCR, olmOCR, and PaddleOCR-VL are vision-language models and need a GPU for practical throughput. olmOCR, for example, asks for a recent NVIDIA GPU with at least 12 GB of VRAM.

The pattern is simple: classic engines and text-layer parsers run on CPU, and vision-language models need a GPU. If you have no GPUs and your documents include scans with tables or handwriting, that gap is usually where a managed service such as LlamaParse earns its cost.

Can I use open-source OCR for commercial applications?

Usually, yes. All seven tools on this list use the Apache 2.0 or MIT license, and both allow commercial use, modification, and redistribution.

Two things are worth checking before you ship. First, model weights can carry a different license from the code, so read both. Second, some other OCR projects use copyleft or revenue-capped licenses, which can restrict closed-source or larger commercial use. Open source also leaves accuracy, uptime, and data handling with you, since there is no vendor service-level agreement behind it.

What are the pros and cons of self-hosting OCR?

The advantages:

  • Documents never leave your infrastructure.
  • No per-page fees or API rate limits.
  • You can fine-tune models and control every step of the pipeline.

The costs:

  • You run and scale the compute, including GPUs for vision-language models.
  • You own upgrades, monitoring, retries, and failure handling.
  • Accuracy on hard documents varies by tool, so quality checks are your job.

Self-hosting fits best when data cannot leave your environment or when volume is high and documents are predictable. When engineering time is the constraint, a managed parser is usually cheaper overall.

What output formats do open-source OCR tools support?

It depends on the generation of the tool.

  • Classic engines return text with positions: Tesseract outputs plain text, hOCR, TSV, ALTO, or searchable PDF, and EasyOCR returns bounding boxes, text, and confidence scores.
  • Document parsers return structure: LiteParse outputs text, Markdown, or JSON with bounding boxes, Docling exports Markdown, HTML, DocTags, or JSON, and PaddleOCR's PP-StructureV3 produces Markdown or JSON.
  • Vision-language models return Markdown: DeepSeek-OCR adds grounding boxes, and olmOCR writes Markdown in reading order.

If you need specific fields pulled into a schema, plan a separate extraction step on top of the parsed output.

How do I benchmark OCR tools on my own documents?

Build a small test set first: 50 to 100 pages that represent your real mix, weighted toward the hardest layouts. Write down the correct output for the things you care about, such as totals in tables, reading order on multi-column pages, or values in forms.

Run every candidate on the same pages and score what matters to your application, not just character accuracy. Check whether numbers are right, whether tables keep their rows and columns, whether text arrives in reading order, and whether anything was invented or dropped. Track speed and cost per page alongside quality.

Public benchmarks help you narrow the field before you test. ParseBench scores parsers on tables, charts, content faithfulness, formatting, and visual grounding, olmOCR-Bench and OmniDocBench are widely used for document parsing, and ExtractBench covers structured extraction from enterprise documents.

What is the difference between traditional OCR and agentic document processing?

Traditional OCR is mainly focused on converting pixels into text. It works reasonably well when documents are clean, simple, and consistent, but it often breaks down when pages include multi-column layouts, nested tables, charts, forms, footnotes, equations, or mixed visual elements. In those cases, you may still get text back, but the output is often flattened, out of order, and difficult for downstream systems to use reliably.

Agentic document processing goes further. Instead of only recognizing characters, it tries to preserve the document’s structure and meaning so the result is usable inside AI pipelines. That usually includes:

  • Maintaining reading order across complex layouts
  • Preserving headings, sections, lists, and table relationships
  • Distinguishing text from charts, formulas, and images
  • Producing structured output such as Markdown or JSON
  • Supporting multi-step extraction workflows and field-level confidence

For developers building document extraction pipelines, document agents, or LLM-based automation, this difference is important. A raw OCR transcript might be technically correct at the word level but still be poor input for retrieval or reasoning. A structure-aware parser is often much more useful because it gives your application cleaner chunks, better citations, and more reliable semantic boundaries.

What output format is best for LLM applications: plain text, JSON, or Markdown?

For most LLM workflows, structured Markdown or well-formed JSON is usually better than plain text.

  • Plain text is easy to generate, but it often loses the very signals that help retrieval and reasoning work well, such as:
  • document headings
  • table structure
  • bullet lists
  • section boundaries
  • captions and footnotes
  • reading order across complex layouts

Markdown is often a strong default because it stays human-readable while preserving useful document structure. It works well for chunking, indexing, prompting, and debugging. That is why Markdown-first outputs are attractive in tools such as LlamaParse, DeepSeek-OCR’s grounded Markdown workflows, and Docling.

JSON is better when you need deterministic downstream extraction, typed fields, or direct application logic. For example, if you are populating a database with invoice totals, claim IDs, or patient fields, JSON may be the better target format.

A practical pattern is:

  • use Markdown for retrieval, summarization, and general-purpose LLM context
  • use JSON for field extraction, workflow automation, and application integration
  • avoid relying on plain text only for structure-heavy documents unless the source documents are very simple

If your end goal is a production AI workflow, the best OCR output is usually the one that minimizes cleanup and preserves enough structure that your LLM can reason over the document without guessing what belonged where.
